# CardDAV protocol — read-write contact sync

Expose the contacts data model built in #79 over CardDAV (RFC 6352), so external clients (DAVx5, Apple Contacts, Thunderbird, most mobile address book apps) can sync tidl's address book directly, the same way they already sync tidl's calendars over CalDAV.

## Dependencies

- [79 - Contacts data model + Contacts tab](79-contacts-data-model-tab.md) — the `contacts`/`contact_emails`/`contact_phones` tables and CRUD API this protocol layer serves.

## Context / Background

This item began as a research spike (see history below) that concluded full protocol support wasn't worth it for internal-only synergies. It's being revived because the ask this time is explicit: a real Contacts tab *and* CardDAV sync, not just an internal contacts model. #79 covers the tab/CRUD; this item covers making that address book speak CardDAV.

CalDAV precedent to mirror: `crates/tidl-caldav` (pure protocol library, no Leptos/Axum/sqlx) + `tidl-server`'s CalDAV route handlers, using `username:app_token` HTTP Basic auth (the same App Tokens panel in Settings already provisions these — no new secret material needed for CardDAV, just documenting the CardDAV URL alongside the existing CalDAV one).

### Original spike findings (2026-06, before this was dropped and reopened)

- CardDAV's wire operations (PROPFIND, REPORT, GET/PUT/DELETE with ETag concurrency) are structurally the same shape as CalDAV's — just vCard payloads instead of iCalendar.
- A new `tidl-carddav` crate (mirroring `tidl-caldav`) is the right boundary: vCard parse/serialize + DAV XML handling, no framework/db deps.
- DB schema implications are now resolved by #79 rather than open — see that item's data model.

## Functional Requirements

- **New crate: `tidl-carddav`** (workspace addition — flagged per CLAUDE.md §19, requires sign-off, given here via spec approval). No Leptos, no Axum, no sqlx, per the same library rules as `tidl-caldav` (CLAUDE.md §11). Provides vCard 3.0/4.0 parse/serialize and CardDAV XML (PROPFIND/REPORT) handling.
- **`tidl-server` routes** under `/carddav/{username}/contacts/...`, mirroring `caldav_handlers.rs`'s structure:
  - `PROPFIND` — address-book discovery (`.well-known/carddav`, `current-user-principal`, `addressbook-home-set`, matching the standard discovery chain noted in #61).
  - `REPORT` (`addressbook-query` / `sync-collection`, RFC 6578) for incremental sync.
  - `GET`/`PUT`/`DELETE` per-contact vCard, with ETag concurrency (reuse `contacts.etag` from #79's schema).
- **Read-write**: clients may create/edit/delete contacts via CardDAV; changes sync back into tidl's `contacts` tables (full read-write, matching how CalDAV already behaves for calendars — not read-only).
- **Auth**: reuse the existing `username:app_token` HTTP Basic scheme (same App Tokens panel, no new UI needed beyond documenting the CardDAV URL).
- **Sync token**: add the per-user address-book sync-token column (deferred from #79) needed for `sync-collection` REPORT, following the same `bump_calendar_sync_token`-style helper pattern used for calendars.
- Map DB rows ↔ vCard at the infrastructure boundary in `tidl-server` (per CLAUDE.md §11 — no sqlx types leak into `tidl-carddav`).

## Why dropped (original, 2026-06-21) — superseded, item reopened 2026-09-14

CardDAV as a sync protocol is significant scope for a personal calendar + tasks tool. The meaningful synergies (iMIP attendee resolution, wikilink-to-person) don't require the full CardDAV protocol — they only need an internal contacts data model. Full protocol support is only worth it to replace Nextcloud as a single DAV endpoint, which is out of scope for tidl's goals.

This reasoning no longer applies: the current ask explicitly wants CardDAV sync (not just an internal model), so the protocol work is now in scope. #79 supplies the internal contacts model this item builds on.

## Resolution

Built largely as specified, with a few scope/design decisions made during implementation (agreed via a plan-mode review before coding):

- **New crate `tidl-carddav`** (`crates/tidl-carddav/`): `vcard.rs` (vCard 3.0 parse/serialize — `VCardFields`/`VCardMethod`, RFC 6350 folding/escaping, round-trip tested), `carddav.rs` (`addressbook-query`/`addressbook-multiget` REPORT parsing + response generation, mirroring `tidl-caldav::caldav`), `xml.rs` (CardDAV multistatus/PROPFIND XML with the `CARD:` namespace). One deviation from the original spec bullet: **`tidl-carddav` depends on `tidl-caldav`** (a new crate-to-crate edge, now documented in `.claude/CLAUDE.md` §1/§6) to reuse the generic, non-calendar-specific WebDAV PROPFIND/PROPPATCH parsing and ETag machinery rather than re-implementing ~500 lines of quick-xml handling — only the multistatus *response* envelope (which declares different XML namespaces) is CardDAV's own code.
- **Routes** (`crates/tidl-server/src/carddav_handlers.rs`, new): `/carddav/{username}/` (home) → `/carddav/{username}/contacts/` (the one address book, matching the spec's literal route shape) → `/carddav/{username}/contacts/{uid}.vcf` (vCard resources), plus `/carddav/principals/{username}/` and `.well-known/carddav` discovery (previously incorrectly redirected to the CalDAV root — fixed as part of this item). **Scope reduction from the CalDAV mirror**: no LOCK/UNLOCK, COPY/MOVE, or MKCOL — RFC 6352 sync clients don't need WebDAV locking, and there's exactly one address book per user with no multi-collection use case, so those verbs have nothing to operate on. `OPTIONS` advertises the smaller, truthful verb set.
- **Storage**: new `ContactStore` trait (`crates/tidl-server/src/storage.rs`, separate from `CalendarStore` — different resource, avoids bloating an already-2000+-line trait) backed by the same `Storage` struct, wired into `AppState.contacts`. New `address_books` (one row per user, `sync_token`) and `contact_sync_log` tables (`migrations/20260915000000_carddav_sync.sql`), mirroring `calendars.sync_token`/`sync_log` for RFC 6578 `sync-collection`. **Important correctness fix beyond the literal spec**: `contacts.uid` is globally unique (not unique-per-owner, per #79's schema), so a naive `ON CONFLICT(uid) DO UPDATE` upsert on `store_contact_vcard` would let one user's PUT silently overwrite a different user's contact on a UID collision. Guarded explicitly with a `UidOwnershipConflict` typed error, checked in the same transaction as the upsert, mapped to `403 Forbidden` at the handler layer.
- **Username rename cascade**: `address_books.owner_username` and `contact_sync_log.owner_username` added to `tidl-web/src/api/profile.rs`'s `USERNAME_COLUMNS` (caught immediately by that file's own exhaustiveness test, same as #79's `contacts.owner_username` before it) — a rename now correctly cascades to CardDAV's own bookkeeping tables too.
- **No SSE push on CardDAV writes** — #79's own in-app Contacts CRUD never wired up live SSE refresh either (verified: no `change_tx` use in `api/contacts.rs`), so there was no existing plumbing to extend; CardDAV clients rely on `sync-collection` polling regardless, matching how they behave against any other CardDAV server.
- **Docs**: README's Contacts/CardDAV feature bullets and Mobile Setup section updated with the `/carddav/username/contacts` URL; the username-rename warning in `profile_modal.rs` now mentions the CardDAV address too.
- **Follow-up fix #1 (found during real-client verification, 2026-09-15)**: contacts created/edited/deleted through the web UI's own `api/contacts.rs` (`create_contact`/`update_contact`/`delete_contact`) never bumped `address_books.sync_token` or logged to `contact_sync_log` — those functions predate this item and write directly via their own SQL, bypassing `ContactStore` entirely (tidl-web can't depend on tidl-server). Fixed by adding a duplicate `bump_contacts_sync_token` helper in `api/contacts.rs` (same duplication-across-the-compilation-boundary reasoning as `notify_calendar_watchers`), called after every web-UI create/edit/delete.
- **Follow-up fix #2 (found via real Thunderbird testing, same day)**: `carddav_sync_collection`'s response XML wrapped an extra, non-standard `<D:response>` for the *collection itself* around the `<D:sync-token>` value, nesting it inside a `<D:propstat>` — a deviation from the `caldav_sync_collection` precedent it was supposed to mirror (RFC 6578 §3.6 wants `sync-token` as a direct child of `multistatus`). Fixed by extracting the response assembly into two pure, unit-tested functions (`parse_sync_token_from_body`, `format_sync_collection_multistatus`) and dropping the bogus entry. This alone didn't fix the user's actual symptom, though — see fix #3.
- **Follow-up fix #3 (the actual root cause of "zero contacts sync tidl→Thunderbird", found the same day by first fixing `trace_layer.rs`'s `is_caldav` path filter — it only matched `/caldav`/`/.well-known`, silently excluding every `/carddav` request from the debug trace logging used to diagnose this in the first place)**: `build_addressbook_propstats` emits a `getctag` property with `namespace: "CS"`, but `tidl_carddav::xml::generate_propfind_response`'s multistatus envelope only declared `xmlns:D`/`xmlns:CARD` — never `xmlns:CS`. Every PROPFIND response for the address-book collection (and, nested, the home collection) was therefore invalid XML: an element with an undeclared namespace prefix. Real clients don't surface this as a visible error — Thunderbird's sync engine just silently abandons the whole sync after the malformed PROPFIND, which is exactly what was observed (PROPFIND on `/carddav/{user}/contacts/` returns `207`, and nothing — no REPORT, no GET — ever follows, on the initial sync or any manual resync). Fixed by declaring `xmlns:CS="http://calendarserver.org/ns/"` in the CardDAV envelope (matching CalDAV's own, which already declares it). Added a namespace-resolution test (`assert_namespaces_are_declared`, using `quick_xml::NsReader`) alongside the existing plain well-formedness check — the latter alone can't catch this bug class, since basic XML well-formedness doesn't validate namespace bindings. This was the actual fix that got real client sync working.
- **Infra fix, found along the way**: `flake.nix`'s `prepare-sqlx` dev-shell script only ran `cargo sqlx prepare` against the lib/bin target, silently dropping `query!`/`query_scalar!` calls inside `#[cfg(test)]` blocks from the offline query cache (`SQLX_OFFLINE=true`) — every test-only query in the codebase, not just this item's new ones, was exposed to this. Fixed by passing `-- --tests` through to `cargo sqlx prepare`.
- **Follow-up fix #4 (2026-09-17, found chasing an iOS Contacts hang — spinner forever, tidl's log goes quiet, then iOS's misleading "Cannot connect using SSL" dialog)**: `parse_propfind` (`tidl-caldav/src/webdav.rs`, shared by CalDAV and CardDAV) lowercased every requested property *name*, not just the structural keywords (`propfind`/`prop`/`allprop`/`propname`). Several DAV: properties aren't all-lowercase — `principal-URL` (RFC 3744 §4.2) has a capital URL — so a client asking for `principal-URL` got told about `principal-url` instead: a different, case-mismatched element name that a case-sensitive XML client never recognises as an answer to its own question, confirmed with a raw `curl -v PROPFIND` capturing the exact response. Fixed by preserving the client's original case when extracting property names (`local_name_preserving_case`, new) while keeping keyword matching case-insensitive, and updating both comparison sites (`carddav_handlers.rs`'s `split_found_propstats`, `caldav_handlers.rs`'s `build_principal_propstats` — CalDAV's own `build_calendar_propstats` already lowercased at comparison time and needed no change) to lowercase explicitly at lookup rather than assume the parser already had. Added an end-to-end test (`carddav_root_propfind_end_to_end_preserves_requested_case`) after noticing the first regression test for this only exercised the splitting logic in isolation with a hand-built request, never actually through the parser where the real bug lived — confirmed it fails without the fix and passes with it.
- **Follow-up fix #5 (2026-09-17, same iOS hang — fix #4 alone didn't resolve it; the discovery chain up through `OPTIONS /carddav/principals/{user}/` kept succeeding but the client still never proceeded)**: `carddav_options` advertised `DAV: 1, addressbook-access` — copying CalDAV's `calendar-access` compliance-class token by analogy. RFC 6352 §10.1 defines the actual CardDAV token as the literal string `addressbook`, with no `-access` suffix (unlike CalDAV's RFC 4791 token, which genuinely is `calendar-access`). A client checking that exact token to confirm CardDAV support never finds it — `addressbook-access` doesn't equal `addressbook`, even though it contains it as a substring, which is exactly why the regression test asserts an exact comma-separated token match rather than `.contains()`. Fixed to `DAV: 1, addressbook`.
- Verified end-to-end via `cargo test --workspace` (587 tests, covering all five follow-up fixes), `cargo clippy --workspace -- -D warnings`, and `cargo build --target wasm32-unknown-unknown -p tidl-web` — all clean.
- **Real-client verification (2026-09-15–17): confirmed bidirectional sync against Thunderbird**; iOS Contacts discovery chain fixed per #4/#5 above, full round-trip verification against iOS still pending re-test. DAVx5/Apple macOS Contacts remain unverified; revisit if either surfaces its own quirks (see #85).
- **Follow-up: extended vCard field support + multi-address bug fix (2026-09-17, found continuing iOS testing after #4/#5)**: adding a URL to a contact on iOS synced fine to iOS but tidl silently dropped it on parse — tidl's contact model only ever captured `UID`/`FN`/`N` (given+family only)/`ORG`/`TITLE`/`BDAY`/`ADR`/`EMAIL`/`TEL`/`NOTE`. Worse, `ADR` was a **real bug**, not just a gap: iOS can attach multiple addresses (home/work), but `parse_vcard` unconditionally overwrote a single flat `street`/`city`/`region`/`postal_code`/`country` on every `ADR` line — only the last one in the vCard survived, the rest silently vanished. Fixed by adding the confirmed-safe field set (agreed via plan-mode review; deferred `X-SOCIALPROFILE` and `RELATED`/`X-ABRELATEDNAMES` to a follow-up since those are undocumented Apple encodings unverifiable without another live-device round-trip — see #85; `PHOTO` stays out per #79's own decision, no blob storage infra exists):
  - **Schema** (`migrations/20260917000000_contacts_extended_fields.sql`): `contacts` gains `middle_name`, `name_prefix`, `name_suffix`, `nickname`, `anniversary`; new `contact_addresses`, `contact_urls`, `contact_impps`, `contact_categories` child tables (mirroring `contact_emails`/`contact_phones`'s shape). Existing single-address data backfilled into `contact_addresses` before the old flat `street`/`city`/`region`/`postal_code`/`country` columns were dropped (SQLite `ALTER TABLE … DROP COLUMN`, supported since 3.35).
  - **`tidl-carddav::vcard`**: rewritten to a two-pass parser to handle Apple's `itemN.PROPERTY` + `itemN.X-ABLabel:_$!<Label>!$_` grouped-label convention (confirmed live for `URL`: `item2.URL;type=pref:https://…` + `item2.X-ABLabel:_$!<HomePage>!$_` — the item-group syntax is standard RFC 2426 §4, Apple's label-pairing convention on top of it is proprietary but not obscure). First pass collects `itemN` → decoded label; second pass resolves URL/IMPP kind from `TYPE=` first, falling back to a case-insensitive substring match on the label, else `"other"`. `ADR` now pushes to a `Vec<VCardAddress>` instead of overwriting flat fields — the actual regression test for the reported bug. `ANNIVERSARY` accepts a plain vCard-4-style property directly, and separately maps `X-ABDATE` to anniversary only when its paired label contains "anniversary" (case-insensitive) — this path is a reasoned guess, not verified against real device data, since only the `URL` item-group format was confirmed live; flagged here for re-verification alongside #85.
  - **`tidl-server`**: `ContactRecord`/`ContactAddressRecord` extended; `storage.rs`'s existing delete-then-reinsert transaction pattern (already used for emails/phones) extended to the four new child tables; `carddav_handlers.rs`'s `record_to_vcard` maps every new field through.
  - **`tidl-web`**: `ContactDto`/`NewContact` gain the new fields plus a `Vec<ContactAddress>` (replacing the old flat address fields); `api/contacts.rs`'s CRUD extended to the new columns/child tables; `contact_editor_modal.rs` gains new inputs (name prefix/suffix/middle, nickname, anniversary, comma-separated categories, reused `ContactMethodRows` for URLs/IM) and a new `ContactAddressRows` component (mirrors `ContactMethodRows`'s add/remove/`<For>`-keyed-by-index structure, but each row is a street/city/region/postal/country mini-form with a home/work/other kind picker); `contact_card.rs` shows a contact's nickname next to its name and its primary URL as a link, keeping the card itself light — full detail stays in the editor modal.
  - Verified via `cargo test --workspace` (593 tests, including new `tidl-carddav` tests for every new field, the exact iOS URL item-group wire format, and the multi-address regression test; new `tidl-server` storage/handler tests covering the extended-field round trip and update-replaces-not-accumulates), `cargo clippy --workspace -- -D warnings`, and `cargo build --target wasm32-unknown-unknown -p tidl-web` — all clean. Self-round-trip only (create/edit a contact in the web UI using every new field, confirm it PUTs/GETs back unchanged) — a live iOS re-test of a URL, anniversary, second address, and nickname added from the phone is still pending; tracked in #85.
