# @mention contact linking in notes

Typing `@` in the note editor opens a filterable popup of contacts; picking one inserts `@Contact Name` as plain text. In the rendered note view, a resolved mention is clickable and opens a small contact-detail popover in place.

## Dependencies

- [79 - Contacts data model + Contacts tab](79-contacts-data-model-tab.md) — the contacts this feature links to.

## Context / Background

Requested alongside #29/#79 as the first (deliberately limited) integration point between Contacts and Notes: "for now integration is limited, but it would be nice if you can @<contactname> on a note... and it will pop up a list you can filter down by typing." Mirrors the existing `[[wikilink]]` pattern (#33) closely enough to reuse its lessons:

- **Storage**: plain `@Jane Doe` text in the note's markdown, not a structured ID token — resolved by name lookup at render time (same choice #33 made for `[[link]]`, and for the same reason: no schema change, no ID-drift risk to design around, though it does mean a contact rename breaks existing mentions until re-typed — same trade-off wikilinks already accept for file renames).
- **Click behavior**: unlike `[[wikilink]]` (which navigates in-place with a back stack), a resolved `@mention` opens a small contact-detail popover without leaving the note — decided during design because contact info is meant to be a quick glance, not a destination.
- **Popup anchoring**: decided (via mockup) to anchor at the caret (Slack/GitHub-style), not fixed below the textarea. Since the note editor's text input is a plain `<textarea>` (`note_editor_modal.rs:247`, no rich-text component), this requires caret-coordinate calculation — the standard "mirror div" technique (an offscreen div matching the textarea's font/padding/wrapping, with a marker span at the caret's text offset, whose position is read via `getBoundingClientRect()`). This is DOM measurement, so it's `#[cfg(feature = "hydrate")]`-only per CLAUDE.md §15's window/DOM rule.

## Functional Requirements

- Typing `@` in the note textarea (create or edit) opens a popup listing contacts, anchored at the caret.
- Typing after `@` filters the list by name (substring/prefix match); arrow keys + Enter to select, Escape to dismiss.
- Selecting a contact inserts `@{display_name}` at the caret, replacing the in-progress `@filter` text, and closes the popup.
- In the rendered markdown view, `@Name` that resolves to an existing contact (case-insensitive match against `contacts.display_name`, scoped to the note owner's own address book — no cross-user lookup) renders as a styled, clickable span (mirrors `[[wikilink]]`'s `<button data-*>` click-delegation approach, since rendered HTML is injected via `inner_html` and can't carry Leptos `on:click` handlers directly).
- Clicking a resolved mention opens a popover showing that contact's card content (same fields as the Contacts tab's card — org, emails, phones, notes).
- An `@Name` that doesn't resolve to a contact renders as plain text (no false-positive styling on ordinary `@` usage, e.g. email addresses or social handles typed into notes) — resolution requires an exact (case-insensitive) name match, not just any `@word`.

## Open Questions

- Ambiguous names (two contacts named "Jane Doe"): out of scope for v1 — first match wins; a disambiguation UI is a follow-up if it comes up in practice.
- Should the popup also suggest contacts on partial mid-name matches (e.g. `@doe` matching a family name), or prefix-of-display-name only? Left to implementation; not a spec-blocking decision.

## Resolution

Built as specified, with one scope clarification made explicitly and one architectural discovery, both worth recording:

- **Scope clarification: "the rendered note view" didn't exist yet.** The spec's Context/Background assumed mentions would render "mirror[ing] the existing `[[wikilink]]` pattern" — but wikilinks in this app only render inside the markdown-*source-file* preview modal (`components/focus.rs`'s `MarkdownPreviewInner`, reachable from Focus/Tasks/Await); the Notes tab itself has never rendered markdown at all — `NoteCard`'s body and the editor's `<textarea>` are both plain text, today and before this change. Rather than silently bundling "add full CommonMark rendering to Notes" into this item (a much larger, unrequested feature), the resolution scopes narrowly to what backlog #80's own title asks for: `NoteCard`'s text display gained a *mention-only* rendering pass (`render_note_mentions`) — HTML-escaped plain text with just `@Name` spans substituted for resolved mentions — not a markdown parser. Everything else in a note's body (headings, bold, wikilinks, etc.) still renders as literal text in the Notes tab, unchanged from before this item.
- **Architectural discovery: `tidl-markdown` isn't actually wasm32-safe**, despite CLAUDE.md §1's project-identity table claiming otherwise for every library crate. `cargo build --target wasm32-unknown-unknown -p tidl-markdown` fails outright — its `sync_engine` pulls in `tokio` (full, networking-enabled) and `notify` (filesystem watching), neither of which compile to `wasm32-unknown-unknown`. Since mention rendering needs to run client-side (per-`NoteCard`, reactively, against an already-fetched contact list — a server round trip per card would misalign with the masonry grid's synchronous content-height self-correction pass), `render_note_mentions`/`find_active_mention` were written as new, dependency-free pure functions directly in `tidl-web/src/util.rs` rather than added to `tidl-markdown` — sidestepping the incompatibility entirely rather than trying to fix it (out of scope here). CLAUDE.md §1 was left as-is (not this item's concern to correct), but a future crate audit should know `tidl-markdown` is `ssr`-only in practice.
- **Duplicate-name handling**: "first match wins" exactly as the spec's own Open Questions section calls for — `find_contact_by_name`/`resolve_contact_mention` (`api/contacts.rs`) pick the lowest-id match, no disambiguation UI.
- **`#[server] resolve_contact_mention(name) -> Option<ContactDto>`** (`api/contacts.rs`): case/whitespace-insensitive lookup scoped to the caller's own address book (`find_contact_by_name`, unit-tested directly per this file's established "test the ssr helper, not the `#[server]` wrapper" convention).
- **Rendering** (`util.rs::render_note_mentions`): longest-name-first matching (so "Jane" doesn't shadow "Jane Doe"), boundary checks on both sides of a match (`@` must start the text or follow whitespace — so `foo@example.com` never triggers; the character after a match must not be alphanumeric — so "Jane" never swallows into "Janet"), full Unicode case-insensitivity (not just ASCII), HTML-escaped everywhere else. Output is a `<button class="md-mention" data-mention="...">` — the same click-delegation shape `tidl_markdown`'s `[[wikilink]]` uses, for the same reason (the string is injected via `inner_html`, which can't carry a Leptos `on:click`).
- **`NoteCard`**: the text div's `on:pointerdown` stops propagation only when the target has `data-mention` (so a mention click can't also trigger the card's own drag/click-to-edit pickup, which is bound on the same event at the card root) — mirrors the pin star's existing identical technique. `on:click` walks up from the click target for `data-mention`, resolves it via `resolve_contact_mention`, and opens `MentionPopover` (new, `components/notes/mention_popover.rs`) positioned at the clicked span's `getBoundingClientRect()`. Contact names feed in via a new `ContactsRefresh`-independent signal in `NotesView` (`list_contacts()` behind a plain reactive `.get()`, not `Suspend::new`, so a slow contacts fetch never suspends the notes grid — leptos-suspense skill), fed through an `Effect` so a contact rename/delete updates every card's mentions without waiting on the notes list's own refresh cycle.
- **Editor typeahead** (`note_editor_modal.rs`): `@` detection (`find_active_mention`, `util.rs`) runs on every `input`/`click` on the textarea. Popup position is computed via the standard "mirror div" technique — an offscreen div copying the textarea's font/box CSS, filled with the pre-caret text plus a zero-width marker span, whose `getBoundingClientRect()` gives the caret's viewport coordinates (`caret_client_coords`). `ArrowUp`/`ArrowDown`/`Enter`/`Escape` are intercepted on `keydown` only while the popup is open (`prevent_default`, so Enter doesn't also insert a newline); selecting (via Enter or a mouse `mousedown` + `preventDefault`, so the textarea never loses focus) replaces the `@query` span with `@{display_name} ` and restores focus/caret one tick later (`set_timeout(…, 0)`, same deferred-DOM-sync technique already used for the wikilink pill-flash in `focus.rs`) since the DOM's `.value` hasn't caught up to the signal write yet at the moment the handler runs.
- **Popup result ordering/cap**: prefix matches before other substring matches, then alphabetical; capped at 8 rows with a scrollable popup — not spec-mandated, a reasonable implementation default per the Open Questions' explicit "left to implementation."
- **New `tidl-web` dependency surface**: `KeyboardEvent` and `Text` added to `web-sys`'s feature list (Cargo.toml) — feature flags on an already-present dependency, not a new crate, so no CLAUDE.md §19 sign-off sought (unlike #87's `tidl-carddav` addition, which *was* a new cross-crate edge).
- **Testing**: 16 new unit tests — 8 for `render_note_mentions` (case-insensitivity, longest-match, email/word-boundary false-positive avoidance, HTML escaping), 7 for `find_active_mention` (the editor-trigger heuristic), 1 for `find_contact_by_name` (case/whitespace-insensitive, owner-scoped). Full `cargo test --workspace` (379 tidl-web tests, 629 total), `cargo clippy --workspace -- -D warnings`, and `cargo build --target wasm32-unknown-unknown -p tidl-web` all pass/build clean, checked additionally with `--features ssr` and `--features hydrate --target wasm32-unknown-unknown` (both also clean) since this item's code is split across both compilation targets more than most.
- **Manual browser verification not completed** — the Claude-in-Chrome extension was unavailable in this session (checked twice). This item carries meaningfully more unverified runtime risk than most: the caret-mirror-div coordinate math and the pointerdown/click delegation around the card's existing drag system are both novel-to-this-codebase DOM interactions with no unit-test coverage (only the pure string-matching logic was testable). Flagged explicitly to the user rather than claimed as working; a real click-through (typing `@`, arrow-key nav, Enter-to-insert, clicking a rendered mention) is the recommended next step before relying on this.

### Follow-up (same day, live user testing)

The user manually verified the editor typeahead and mention rendering worked correctly, then asked for the popover to show more detail and to add a "go to the real contact" link — with the same scroll-to-center-and-flash treatment notes get when opened via Focus's "↗ Go to source" (backlog #62/#74).

- **`MentionPopover`** (`mention_popover.rs`) now shows the full detail set: nickname, birthday/anniversary, categories (as small pills), all URLs (clickable) and IM handles (not just emails/phones), and formatted postal addresses (`format_address`, unit-tested) — a genuinely broader "detail" view than the Contacts-tab card itself, which stays compact by design.
- **"Go to contact →"** is a plain `<a href="/contacts?highlight={id}">` (full-page navigation, no JS) — same mechanism `NoteGotoModal`'s "Show in collection" button uses for `/notes?highlight=`, just as a real link instead of a button+`window.location` call since there was no reason not to let the browser handle it natively here.
- **`ContactsView`** (`components/contacts/mod.rs`) gained the same one-shot `?highlight=` deep-link effect `NotesView` already had for #63 — reads the query param on mount, waits for the target contact to appear in the rendered grid, then scrolls and pulses it. One deliberate difference from the Notes version, per this feedback: centers the card (`ScrollLogicalPosition::Center` + `ScrollBehavior::Smooth`) rather than top-aligning it (Notes' original `scroll_into_view_with_bool(true)` was left unchanged — out of scope, not requested). The pulse (`.contact-card--highlight`, `contact-highlight-pulse` keyframes) mirrors `.note-card--highlight` exactly, but uses the fixed `--primary-color` instead of a per-instance CSS variable, since contacts have no collection (or other per-item color) to borrow from.
- 4 new tests for `format_address`. Full `cargo test --workspace` (383 tidl-web tests, 633 total), clippy, and all four build configurations (ssr / no-features / wasm32 / wasm32+hydrate) still clean. This follow-up itself was not clicked through in a real browser either (extension still unavailable) — same caveat as above, now covering more surface.

### Bugfix: the pulse never actually appeared

The user confirmed the navigation/scroll worked but the flash didn't. Root cause: the pulse was applied by an imperative `classList.add("contact-card--highlight")` inside the same effect that scrolls — but `ContactsView`'s card list (`contacts.into_iter().map(...).collect_view()`) is unkeyed, and the height self-correction pass right below that effect reacts to the exact same `contacts_display` change (the target contact becoming visible for the first time almost always needs its span corrected) by writing back to `contacts_display`, which remounts the *entire* card list from scratch — silently destroying the just-added class on a DOM node that was about to be thrown away, before the user ever saw it. (`notes::NotesView`'s original `?highlight=` effect has the identical `classList.add` + adjacent self-correction-remount shape; it likely just avoids hitting the race as reliably in practice.)

Fixed by making the pulse reactive instead of imperative: `ContactCard` now takes a `highlight_id: RwSignal<Option<i64>>` prop and applies `class=("contact-card--highlight", move || highlight_id.get() == Some(id))` — a Leptos class-toggle binding, evaluated fresh on every render (including a remount), so it survives the self-correction pass' remount instead of racing it. `ContactsView`'s effect now only handles the (still imperative, rAF-deferred) scroll, and clears `highlight_id` via a 2.5s `setTimeout` — matching the pulse animation's real duration (3 × 0.8s) — so the reactive binding, and the whole deep-link, stay genuinely one-shot rather than re-flashing on some later unrelated re-render.

### Verified

The user manually tested the full flow end-to-end in a real browser: `@` typeahead, mention rendering, the detail popover, and "Go to contact" (navigation, centered scroll, and — after the remount-race fix above — the pulse). All confirmed working.
