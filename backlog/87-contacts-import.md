# Contacts import (vCard/CSV)

Let users bulk-import contacts into their address book from an exported file, rather than only via CardDAV sync or one-at-a-time entry in the Contacts tab.

## Dependencies

- [79 - Contacts data model + Contacts tab (CRUD)](79-contacts-data-model-tab.md) — the contact model and store this imports into.

## Context / Background

tidl's Contacts tab (#79) and CardDAV sync (#29) cover creating contacts one at a time or via a live CardDAV client, but there's no way to bring in an existing address book in bulk — e.g. a `.vcf` export from Google Contacts, iCloud, or another CardDAV server, or a `.csv` export from a legacy source. This mirrors #10's calendar-import rationale: most contact managers export standard vCard (RFC 6350) files, so solid `.vcf` import covers the bulk of the ecosystem; `.csv` is lower priority and lossier.

## Functional Requirements

- Upload a `.vcf` file via the web UI (file picker or drag-and-drop), reachable from the Settings modal alongside calendar import.
- Parse all `VCARD` components in the file, mapping into tidl's existing contact fields (name components, org/title, birthday, anniversary, categories, addresses, emails/phones/URLs/IM handles, photo).
- Show a preview (count of contacts found, and how many look like duplicates) before committing.
- Duplicate detection: match on existing contacts by a reasonable heuristic (e.g. full name + a primary email/phone) and offer to skip or overwrite per match, rather than silently creating duplicates.
- Report how many contacts were imported / skipped / failed after the import runs.
- Enforce a file size cap on the upload endpoint, matching #10's precedent.

## Open Questions

- Whether `.csv` import is worth doing at all given how lossy/non-standard it is across sources (Google, Outlook, and generic exports all differ) — likely defer unless a specific need shows up.
- Exact duplicate-matching heuristic — full-name-only will false-positive on common names; email/phone-based matching is more precise but misses contacts with no contact info recorded.
- Whether import should also accept a single `.vcf` containing many `VCARD`s (the common case) vs. requiring one file per contact — assume multi-VCARD-per-file support is required, since that's how every major export works.

## Resolution

Built `.vcf` import as specified; `.csv` stays deferred per the Open Questions above (no change there). One explicit architectural decision made at the user's direction before implementation: **`tidl-web` did not previously depend on `tidl-carddav`** (CLAUDE.md §6's dependency diagram excluded it) even though `tidl_carddav::vcard::parse_vcard`/`generate_vcard` (built for #29/#86) is exactly the vCard mapper this item needs. Asked the user rather than deciding unilaterally, per CLAUDE.md §19's sign-off requirement on new crate dependencies and crate-boundary changes; they chose adding `tidl-carddav` as an `ssr`-only optional dependency to `tidl-web` (mirrors the existing `tidl-caldav` pattern exactly — never compiles to `wasm32`) over the alternative (a new plain Axum route in `tidl-server` duplicating `api/contacts.rs`'s SQL). CLAUDE.md §6's diagram was updated to `tidl-web → tidl-caldav, tidl-carddav, tidl-markdown`.

- **`crates/tidl-web/src/api/contacts.rs`**: two new `#[server]` fns, `preview_vcf_import(vcf_content) -> VcfImportPreview` (read-only: parses, counts, and duplicate-checks without writing) and `import_vcf(vcf_content, overwrite) -> ImportResult` (commits). Both share `split_vcards` (a `BEGIN:VCARD`/`END:VCARD` line-scanner mirroring `api/calendars.rs::split_vcalendar_events`'s approach, minus that function's `VTIMEZONE`-copying complexity, which `VCARD` has no equivalent of), `vcard_to_new_contact` (a field-for-field `VCardFields` → `NewContact` mapper), and `find_duplicate_contact` (the duplicate heuristic below). `create_contact_from_vcard`/`apply_vcard_to_contact` reuse the existing `place_contact`/`replace_methods`/`replace_addresses`/`replace_categories`/`bump_contacts_sync_token` helpers already in this file rather than duplicating `create_contact`/`update_contact`'s bodies.
- **Duplicate heuristic** (`find_duplicate_contact`): matches the spec's own suggested heuristic literally — case/whitespace-insensitive `display_name` equality *and* at least one shared email or phone value; falls back to name-only when the incoming vCard has no email/phone at all (the spec's own acknowledged false-positive risk for common names, accepted deliberately rather than silently importing a likely duplicate).
- **Deviation from the spec's literal wording**: "offer to skip or overwrite per match" was built as a single global skip/overwrite-all toggle instead of a per-contact review step, mirroring #10's calendar import (`import_ics`) exactly — that item's spec used near-identical wording and was itself implemented as a global toggle. A true per-match review screen (checkbox list of found duplicates) would be substantially more UI than this item's scope; global toggle was judged the right trade-off given the established precedent.
- **UI** (`components/settings/import.rs`): the existing `ImportPanel` (previously ICS-only) was split into `IcsImportSection` (unchanged logic, new heading) and a new `VcfImportSection`, both rendered in the existing "Import" Settings tab under `.settings-section-heading` subheadings ("Calendar (.ics)" / "Contacts (.vcf)") — same tab as calendar import, per the spec's "reachable from the Settings modal alongside calendar import." Unlike ICS import, the `.vcf` flow has an extra network round-trip on file selection (`preview_vcf_import`) to compute the duplicate count shown in the preview line, since that requires reading the current address book server-side; the Import button is disabled until that preview resolves.
- **Live refresh**: no cross-component signal previously existed to tell an already-open `ContactsView` to refetch after an external mutation (unlike calendars/events, which have `SidebarRefresh`/`EventsRefresh` in `app.rs`). Added `ContactsRefresh` (`app.rs`, same newtype-context shape, `use_contacts_refresh()` accessor) for this; `ContactsView`'s `LocalResource` now depends on it alongside its own internal `refresh` signal. Deliberately *not* wired into the SSE live-push stream (`EventSource` "cals"/"events"/"all" dispatch) — contacts aren't part of that system at all yet, out of scope here.
- **Size cap**: 10 MB on `vcf_content.len()`, matching `import_ics`'s `MAX_BYTES` precedent exactly, per the spec's explicit instruction to match #10's precedent. (A vCard `PHOTO` embedded in the file is separately capped at 5 MiB decoded, enforced inside `tidl_carddav::vcard::parse_vcard` itself — the same cap #86's web-upload path uses, and an oversized photo is dropped silently rather than failing the whole vCard, consistent with that parser's existing behavior for any unsupported/oversized property.)
- **Testing**: 15 new tests in `api/contacts.rs` — `split_vcards` (multi-vcard files, folded continuation lines, text outside any block), `find_duplicate_contact` (name+email match, name-only fallback, non-matches), and an `import_vcf`-equivalent integration test exercising both the skip and overwrite paths end-to-end against a real `sqlx::test` database (the `#[server]` fn wrapper itself isn't directly testable — same documented work-around this file already uses for `create_contact`/`bump_contacts_sync_token`). Full `cargo test --workspace` (363 tidl-web tests, 613 total across the workspace), `cargo clippy --workspace -- -D warnings`, and `cargo build --target wasm32-unknown-unknown -p tidl-web` all pass/build clean.
- **Manual browser verification not completed**: the Claude-in-Chrome extension wasn't connected in this session, so the UI flow (file picker, preview line, skip/overwrite radios, import) was not clicked through in a real browser — confirmed only via the test suite above plus close parity with the already-shipped, working `IcsImportSection`. Flagged to the user at the time; they accepted proceeding on test-based confidence instead of waiting.
